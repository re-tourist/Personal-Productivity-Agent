# M4 — Failure handling, idempotency, and bounded replanning

This is an **incremental overlay** for the existing `personal-productivity-agent` repository. Do not replace the project or remove M1–M3 files. Copy `src/` and `tests/` into the existing repository; the included `workflows/tool_agent.py` is a **backward-compatible update** that supports optional M4 tools.

## What M4 adds

- `services/task_store.py`: an actual SQLite-backed **local mock task service**, with `tasks` and `task_operations` written inside one transaction. The unique `operation_id` prevents duplicate creates. Same key + different content is rejected.
- `workflows/reliable_task.py`: a LangGraph workflow classifying success, transient failure, and ambiguous commit; reconciling by key; applying a bounded retry; and escalating unknown outcomes. It uses a separate deterministic failure injector only for tests and demos.
- `tools/reliable_task.py`: a single safe `create_task` LangChain tool that exposes only `title` and `due_at`. A trusted application layer injects the stable `operation_id` (not the LLM).
- `workflows/calendar_replanning.py`: reuse M1 when an event conflicts, return an alternative **proposal requiring confirmation**, not a real calendar write.
- `workflows/tool_agent.py`: compatible upgrade of M3 with an opt-in `extra_tools` list. Do NOT also set M3's `allow_mock_writes=True` when adding the M4 tool with the same name.
- `demo_m4.py`: free offline demo by default; `--live` explicitly opts into Qwen API charges.

## Dependencies

Uses your existing M3 `pyproject.toml`: `langgraph`, `langchain-openai`, `pydantic`, `python-dotenv`, and dev/test dependencies. `sqlite3` is in the Python 3.12 standard library. No new third-party requirements are necessary.

In your Conda environment:

```powershell
conda activate ppa
python -m pip install -e ".[dev]"
```

## Offline validation — no Qwen usage

```powershell
python -m pytest -q tests/test_m4_store.py
python -m pytest -q tests/test_m4_graph.py tests/test_m4_calendar_replanning.py tests/test_m4_tool_integration.py
python -m pytest -q
```

Demo of a lost response **after the DB commit** (no model call):

```powershell
python -m productivity_agent.demo_m4 --fault after_commit --operation-id demo-20261103
```

Run exactly the same command again. The second call returns the original task, not a duplicate. By default `--operation-id` is unique per run; supply the same explicit identifier only for retries of the **same logical task**, not for a new task.

Demo of a connection failure **before the commit**, followed by bounded retry:

```powershell
python -m productivity_agent.demo_m4 --fault before_commit --operation-id demo-before-20261103
```

## Optional live Qwen Tool Calling (consumes tokens)

With `.env` and `DASHSCOPE_API_KEY` configured as in M3:

```powershell
python -m productivity_agent.demo_m4 --live
```

Live mode exposes a **single local-mock write tool** and generates a fresh operation ID for the call. There is no real calendar or task service connected. All tests and the default demo are offline and have zero model cost.

## Engineering limitations

1. SQLite mock persistence survives Python restarts on the same machine but is **not** your production PostgreSQL service. It has no authenticated multi-user account isolation.
2. `operation_id` must be persisted by your trusted request coordinator for real retry/resume. A raw LLM tool-call ID is not appropriate. Multiple intentional writes require distinct operation IDs.
3. `before_commit` and `after_commit` fault modes are only synthetic test hooks. Production API gateways need stable idempotency semantics and operation-status reconciliation. A missing record in an eventually consistent external service does **not** guarantee no write occurred.
4. The retry demonstration skips backoff and jitter to remain fast and deterministic. Add exponential backoff for real remote calls; use explicit timeouts. Do not retry write operations against non-idempotent backends.
5. This local SQLite transaction only protects SQLite writes. Side effects spanning different services require a suitable workflow/outbox/saga design; this code does not promise distributed exactly-once execution.
6. LangGraph checkpointer and multi-turn session recovery remain part of M5. Durable operation records are **not** LangGraph checkpoints.

## M4 acceptance criteria

- Same operation ID + identical business request -> one task, same ID.
- Same operation ID + different request -> fails without a new task.
- Timeout after successful commit -> recover by looking up the idempotent operation, no duplicate.
- Failure before commit -> bounded safe retry.
- Concurrent duplicates -> one record, one task.
- Calendar conflict -> propose an alternative, explicitly requiring confirmation.
- M3 Agent can opt into a reliable mock write tool without changing its read-only default.

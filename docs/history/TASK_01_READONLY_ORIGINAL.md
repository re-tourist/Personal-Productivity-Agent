# TASK 01 — 只读根因审计与修复/重写决策

> 优先级：P0；状态：待执行；**本任务不授权 Codex 修改代码**。

## 任务目标

分析 PPA 当前 `python -m pytest -q` 的 `37 passed, 13 warnings, 31 errors`，找出**共享根因和真实影响范围**。对“保留并修复 / 局部重构 / 从零重写”三种方案做基于证据的比较，提出下一轮最小改动方案。不能直接开始修代码。

## 输入资料

- 本地现有仓库（优先级最高），不以历史 ZIP 代替。
- `docs/PROJECT_HANDOFF.md`、`docs/ACCEPTANCE_MATRIX.md`、`AGENTS.md`。
- 用户现有执行事实：离线评测 10/10，Uvicorn 启动完成，访问 `/` 返回 404。
- M7 快照 `docs/architecture.md`, `docs/API.md`, `docs/EVALUATION.md`, `docs/milestones.md`；如本地不存在，请据实说明。

## 操作步骤

1. 核实仓库 Git 状态、当前分支、当前路径、Python 与 Conda 环境、安装依赖及版本、pytest 配置；不要暴露 Key。
2. 先运行 `python -m pytest -q --tb=short` 取得整体分布，再根据需要对出错模块用 `-vv --tb=long -x` 定位首个完整 traceback；保留关键错误原文。
3. 将所有 ERROR/FAILED 按**共同根因**整理，给出每组影响测试数、涉及文件、堆栈证据、可信度。把 warnings 单独归类。
4. 对比代码中的关键接口：`StateGraph`、条件路由、ToolNode、Fake Model、`SqliteSaver` / `AsyncSqliteSaver`、`interrupt` / `Command`、FastAPI 生命周期和依赖注入。不要预设是这些组件出错；逐项证实或排除。
5. 评估测试本身是否正确/过时，与当前 LangGraph 版本的行为是否一致；任何删测建议必须给出技术理由，默认不允许改测试。
6. 对每一种修复策略（A 小修，B 局部重构，C 重写）提供：受影响模块、预计改动范围、风险、可能破坏的回归覆盖和推荐顺序。不必给出不可靠的小时/Token 精确数字，用相对等级即可。
7. 最终输出优先级排序的行动计划，每个修复包有明确测试验收条件；**审计完立即停止**，等待用户/ChatGPT 选择。

## 限制

- 不修改已有源码、测试、依赖文件、README、CI、Git 历史。运行测试产生的非跟踪临时文件可以清理，但不要删除用户数据。
- 不调用真实 Qwen 或其他付费 API。
- 不执行 `git push`、`merge`、`reset --hard`、强制覆盖或仓库重建。
- 不给出缺乏日志证据的“根因已确定”“全量测试已通过”结论。
- `GET /` 的 404 **不是既定缺陷**；先确认 `/app`、`/docs`、`/health` 路由是否按设计存在。

# M5 — Session & Memory: durable HITL approval

This ZIP is an **incremental overlay** for the existing `personal-productivity-agent` repository with M4 already applied. Merge `src/` and `tests/` into the SAME repository. Do not remove M1–M4 files or recreate the Git repository.

## What's new

- `workflows/approval_session.py`: `prepare/validate -> interrupt for user approval -> execute` using `build_reliable_task_graph()` from M4.
- `workflows/chat_memory.py`: `MessagesState` / `add_messages` history within a Thread; free offline illustrative echo responder, **not** a conversational LLM.
- `demo_m5.py`: start one task, exit Python, run a separate Python process for approval/rejection, inspect the persisted thread state.
- `demo_m5_chat.py`: demonstrate short-term conversation history and isolation by `thread_id` across program restarts.
- `tests/test_m5_session.py` and `tests/test_m5_chat_memory.py`: 8 planned framework tests, no LLM usage.

## Architecture and boundaries

**Checkpointer** (`.ppa-data/m5-checkpoints.sqlite`) saves LangGraph state and paused approval position. **M4 business store** (`.ppa-data/tasks.sqlite`) saves durable tasks plus the idempotent `operation_id`. These two databases serve different purposes. Neither SQLite checkpointing nor human approval alone guarantees exactly-once external writes; M4's idempotent transaction is essential.

`thread_id` identifies the persisted LangGraph context. A trusted caller generates/stores `operation_id` for each logical write; it is not the model's tool-call ID. A single demonstration `thread_id` handles ONE approval operation. Do not reuse it for a new operation; use a fresh thread ID for a new approval request.

`interrupt()` is inside a node with **no side effects before it**, because LangGraph re-executes that node from the beginning on resume. The task can only be created after approval; the only write happens in the `execute` node, using M4's idempotency.

A second checkpoint file (`.ppa-data/m5-chat-checkpoints.sqlite`) is used for the educational chat graph because it uses a different State schema; in real systems isolate graphs with appropriate namespace / service boundaries.

## Demo 1 — approve after restarting Python

Run these commands **one at a time**. Each `python -m ...` invocation starts a new Python process.

```powershell
python -m productivity_agent.demo_m5 start --thread-id meeting-001 --title "准备组会" --due-at "2026-12-10T15:00:00+08:00"
python -m productivity_agent.demo_m5 status --thread-id meeting-001
python -m productivity_agent.demo_m5 approve --thread-id meeting-001
python -m productivity_agent.demo_m5 status --thread-id meeting-001
```

After `start`: the run returns `__interrupt__` and `task_count` is unchanged. After `approve`: `status=created` and task count is increased exactly once. A second `approve` on a completed thread is rejected by the CLI. `status` inspects saved execution state without running the graph.

Use `reject` instead of `approve` on a **new** thread to verify that rejection creates no task.

## Demo 2 — chat memory, same Thread vs different Thread

```powershell
python -m productivity_agent.demo_m5_chat --thread-id chat-001 --message "我明天要开组会"
python -m productivity_agent.demo_m5_chat --thread-id chat-001 --message "我之前说了什么？"
python -m productivity_agent.demo_m5_chat --thread-id chat-002 --message "独立会话"
```

Chat demo intentionally does **not** use Qwen; it does not answer intelligently. It only proves persisted messages are merged by `MessagesState` and separated by `thread_id`. For real language understanding, reconnect M3's low-cost Qwen agent in a future integration phase, with a persistent checkpointer.

## Tests

```powershell
python -m pytest -q tests/test_m5_session.py tests/test_m5_chat_memory.py
python -m pytest -q
```

Planned checks:
1. Pause exposes an interrupt and creates no task before approval.
2. Approval creates the task.
3. Rejection leaves task database unchanged.
4. New Python process can resume the same thread with file-backed checkpoints.
5. Same operation ID across two threads is idempotent (M4 integration).
6. Invalid scheduling parameters fail before the approval step.
7. Different threads do not share approval state.
8. Conversation history is merged within one thread, separated between threads and preserved over restarts.

## Limitations / next steps

- All demos run offline: no Qwen API fees and no real calendar/task account writes.
- `SqliteSaver` is for a single-process local demo; use PostgreSQL and async checkpointers as the service scales.
- This milestone implements **thread-scoped short-term memory**. LangGraph **Store** is a separate cross-thread key-value interface for long-term preferences. It is not implemented in this small demo; avoid claiming persistent cross-thread user profiles until implemented and tested.
- No authentication or user-to-thread authorization exists in this CLI prototype. Real APIs must verify the caller may read/approve the requested thread; a guessed `thread_id` is not an authorization credential.
- Concurrent resumes must be serialized/guarded by the server. The M4 `operation_id` handles duplicate business writes but does not prevent conflicting approval decisions in an unprotected service.
- For sensitive long-running workflows, version the workflow definition carefully across deployments; resuming an old checkpoint with incompatible new code is unsafe.
